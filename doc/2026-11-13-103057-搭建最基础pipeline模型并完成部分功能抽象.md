## 1. 背景、现象与调整原因

此前测试 Sensor 已能生成 YUV420 彩条，但由 `app/demo.cpp` 循环调用 `read_frame` 主动读取，HAL 公共层还出现了帧和缓冲定义。这只能展示取帧接口，无法展示参考 sv_element 的“节点绑定后数据自动流转”的模型。

架构偏差在于把测试平台的软件搬运路径当成 HAL 必须提供的数据路径。用户明确：HAL 只管理节点、逻辑端口、连接和生命周期，不处理 buffer；适配层通常也只委托底层绑定，必要时才补充软件处理。真实 SigmaStar VIF、ISP、SCL 的绑定不应被改成逐帧经过 HAL。

本轮目标是最小链路：`color_sensor → file_save`。不加入黑白化 ISP、不实现 sub_pipeline，不扩展实际芯片 SDK。App 搭图后运行 3 秒，再停止、断开、释放。

## 2. 已确认约束与方案演进

| 讨论阶段 | 当前落实方式及原因 |
|---|---|
| App 主动读帧 | 从 Demo 主流程移除，改由 BSP 源节点线程自动分发 |
| HAL 统一帧表示 | 移除此前未提交的 `hal/hal_frame.h` 和 `hal_sensor::read_frame`，避免基础链路依赖软件 buffer |
| 测试后端同步传递到文件 | 文件回调只入队，文件节点另有消费线程，避免生产线程直接承担磁盘写入 |
| 队列满时是否等待 | 丢弃新到帧，保留已经排队的帧，不等待队列空位 |
| 内存池与队列容量 | 两者分别限制为 15；图像缓冲只在初始化时分配，队列存引用 |
| 停止顺序 | 上游先停并等待生产线程退出，下游再排空、结束线程、关闭文件 |
| 文件写入失败 | 文件节点记录本地异常，打印首次写入错误，继续消费，不自动停止 pipeline |
| 通用能力与定制能力 | 保留正式曝光接口和默认不支持的 `custom_process`；本轮自动保存 Demo 不调用定制协议 |

普通文件打开失败属于启动失败：不启动生产源。运行后写失败属于文件节点局部异常：丢弃失败帧并继续运行，用户可以主动停止。

## 3. 分层与两条调用路径

```text
控制路径（App 主线程）
App → HAL pipeline / node / port → test 适配器 → BSP 节点

数据路径（完全位于测试 BSP）
color_sensor::run
    → 填充池中空闲缓冲
    → node::dispatch_frame
    → file_save::data_callback
    → 有界队列
    → file_save::consume
    → write 本地文件
```

HAL 端口没有数据回调、帧或 buffer。`test_endpoint` 只是适配器内部取得 BSP 节点的接口。真正的数据回调是 `test_bsp::node::data_callback`，不暴露到 HAL。

BSP 基类仅服务测试平台。其他平台可以继续复用自己的 element/graph；本次不要求 sv_element 改为继承测试 BSP 基类。

### 5.5 hal/hal_pipeline.cpp：管理、校验、执行顺序与清理

按函数理解：

- `add_node`：拒绝空名字、空节点、重复名字、同实例重复登记和已有 pipeline 归属；仅初始化前可添加。登记成功设置节点归属。
- `remove_node`：当前要求整个 pipeline 未初始化，才清除归属并移除引用。这比“仅停止即可移除”更严格，使用时须先断开并 deinit。
- `get_node`：按名字查找，找不到返回 nullptr。
- `order`：用入度计算拓扑顺序，分叉共享上游只访问一次。独立节点的相对顺序没有业务保证。
- `init`：初始化各节点；失败则逆序 deinit 本次已成功的节点，返回原失败状态。当前 init 在 connect 前，初始化时通常尚无连接，不承诺依据最终拓扑初始化。
- `connect`：仅初始化且停止时允许。校验端口非空、owner、节点真实持有的端口、同图归属、自连接、输入占用；临时加入边并检测环，再调用上游适配器绑定。底层失败移除临时边。
- `disconnect`：运行时拒绝；找到逻辑边后调用适配器解绑，只有成功才移除记录。
- `start`：按拓扑逆序启动，下游先就绪；失败时停止本次已启动节点。只有全成功才设置运行状态。
- `stop`：按拓扑顺序，上游先停止并 join，之后下游排空。已停止时重复调用成功。
- `deinit`：运行中或仍有连接时拒绝，释放成功后清除初始化标志。
- 析构：尽力 stop、disconnect、deinit，并清除节点归属；不是可报告完整清理结果的业务接口，正常路径应显式清理。
- `pause/resume`：目前均返回不支持。

连接逻辑位置见 [pipeline::connect](/home/sunxilong/work/mycode/hal/hal/hal_pipeline.cpp:79)，启动见 [pipeline::start](/home/sunxilong/work/mycode/hal/hal/hal_pipeline.cpp:106)，停止见 [pipeline::stop](/home/sunxilong/work/mycode/hal/hal/hal_pipeline.cpp:124)。

## 7. 逐文件更新：测试 BSP

### 7.1 bsp/test/node.h：软件节点、帧引用与缓冲

新增轻量 BSP 节点基类，声明 init/deinit/start/stop 和可覆盖的 data_callback；提供公共 connect_next/disconnect_next、受保护 dispatch_frame。

`m_input/m_output` 描述数据方向，`m_next` 使用 weak_ptr 保存下游，避免 BSP 节点因连接互相强持有。`m_links_mutex` 保护绑定列表。

测试专用 frame_buffer 保存字节数组和 shared_mutex；frame 保存只读缓冲 shared_ptr、序号、单调时钟微秒时间戳。智能指针决定是否仍有消费者，锁用于显式同步字节访问，两者作用不同。

这里只支持固定 I420，frame 尚无通用格式、尺寸、stride 元数据；不能直接作为后续所有平台的完整媒体帧规范。

### 7.2 bsp/test/node.cpp：实际软件绑定与分发

connect_next 校验源可输出、目标可输入、非自身及非重复绑定；disconnect_next 查找并移除对应引用。

dispatch_frame 在锁内将有效下游提升为临时 shared_ptr，解锁后逐个调用 data_callback。避免持有连接锁调用用户回调。允许一个源绑定多个下游，各下游收到同一图像缓冲的引用。

分发只传递引用，没有整帧 memcpy；临时接收者列表仍可能产生小对象分配，不等于完全无逐帧堆分配。

### 7.3 bsp/test/color_sensor.h：源节点状态与固定规格

`color_sensor : test_bsp::node`，构造为无输入、有输出。固定 width=640、height=480、fps=30、pool_capacity=15，声明产帧线程和 fill_bars。

关键成员：`m_pool` 为预分配缓冲池；`m_thread` 为生产线程；`m_running` 是原子停止标志；`m_wait_mutex/m_wake` 用于周期等待及停止唤醒；`m_produced/m_dropped` 统计成功生成次数、池耗尽跳过次数；`m_exposure_us` 保存模拟曝光值。

### 7.4 bsp/test/color_sensor.cpp：定时生产与池复用

init 在临时容器中申请 15 块 `640*480*3/2=460800` 字节存储，再替换正式池，避免逐帧申请图像内存。像素载荷总计 6,912,000 字节，不含容器、引用计数和锁开销。

start 检查初始化状态，清零统计并创建线程；线程创建异常返回失败。run 每周期查找 `use_count()==1` 的缓冲：此时只有池自身持有，可以写入。填充时取得独占锁，随后构造只读 frame 并分发。池耗尽不阻塞，增加 dropped，在下个周期重试。

fill_bars 直接填充 I420 的 Y、U、V 平面，BT.601 limited-range 八条竖彩条，无显示依赖。Y 占 307200 字节，U、V 各 76800 字节，连续排列，无额外行对齐。

周期使用 steady_clock，时间落后时从当前时刻重新安排下一周期，不集中补帧。m_produced 表示已生成/分发尝试的帧数，不保证所有下游均接收或写入成功。

stop 设置标志、通知等待、join 线程；返回后不会再由该源发出回调。deinit 拒绝运行状态，清除池引用；外部仍持有的缓冲不会因此失效。析构也尝试 stop。

曝光接口检查初始化和 1～1000000 微秒示例范围，只改变模拟参数，不改变彩条亮度。

### 7.5 bsp/test/file_save.h：有界队列与本地异常状态

`file_save : test_bsp::node`，构造为可输入、不可输出。队列容量 15，回调只保存帧引用，线程 consume 执行文件写入。

关键成员：`m_mutex` 保护队列、状态及统计，`m_ready` 通知消费者，`m_queue` 保存待写帧，`m_thread` 为文件线程，`m_path` 为路径，`m_fd=-1` 表示未打开，`m_initialized` 表示初始化，`m_accepting` 表示是否允许入队。

`file_statistics`：accepted 为已入队，written 为完整写入帧，dropped 为队列满拒收，failed 为写失败帧，queued 为当前排队数（不含正在写的帧），peak_queued 为峰值，faulted 为本次运行是否出现文件异常。

### 7.6 bsp/test/file_save.cpp：异步写入、排空和异常处理

set_path 拒绝空路径和文件已打开时更改；init 只设置资源状态，start 才实际 open，以 O_TRUNC 覆盖文件，并创建消费线程。

[data_callback](/home/sunxilong/work/mycode/hal/bsp/test/file_save.cpp:47) 在未接收、空缓冲时拒收；队列满则 dropped++ 并返回 false；否则复制帧描述/智能指针入队，更新统计和通知消费者。

[consume](/home/sunxilong/work/mycode/hal/bsp/test/file_save.cpp:58) 在条件变量上等数据或停止信号，出队后释放队列锁，再持缓冲共享锁写数据。处理短写和 EINTR；写失败记录 failed/faulted，首次打印错误，继续取下一帧。不会让 C++ 异常从文件线程传播到 pipeline。

[stop](/home/sunxilong/work/mycode/hal/bsp/test/file_save.cpp:92) 先禁止新入队，再唤醒消费者。消费者仅在“禁止接收且队列为空”时退出，保证已有帧都被尝试处理。join 后关闭文件；close 失败也仅记录局部异常。

写失败时“排空”表示处理并释放所有已接收帧，不表示这些帧一定保存成功。stop 返回成功也不代表文件无错误，需查看日志或本地统计。

## 8. 完整调用顺序、线程和状态流转

### 8.1 创建和初始化

```text
main → hal::create_factory → test_factory
run_demo → 创建 Sensor / frame sink → 设置文件路径
pipeline.add_node → 持有两节点，登记名字和归属
pipeline.init → 适配器 → BSP.init
    Sensor：分配 15 块图像缓冲
    file：设置初始化标志，不创建写线程
pipeline.connect → 逻辑校验 → test_sensor::connect_next
    → 下游 test_endpoint::bsp_node → BSP.connect_next
```

### 8.2 启动和自动运行

```text
主线程 pipeline.start
    → file.start：打开文件、允许入队、创建文件线程
    → sensor.start：创建生产线程

生产线程：定时生成 → dispatch → file.data_callback → 入队后返回
文件线程：等数据 → 出队 → write → 释放帧引用 → 继续等待
主线程：等待 3 秒，不读写图像
```

### 8.3 停止与释放

```text
pipeline.stop
    → sensor.stop：取消周期等待，join；确认不会再调用下游
    → file.stop：禁止入队，唤醒，消费剩余队列，join，close
pipeline.disconnect → BSP.disconnect_next → 删除 HAL 逻辑边
pipeline.deinit → 释放 BSP 资源
节点退出 pipeline / 析构 → 释放引用
```

管线状态依次为未初始化 → 已初始化 → 已连接（逻辑边非空）→ 运行 → 已停止但仍连接 → 已断开 → 未初始化。当前仅有两个布尔标志和连接集合，不是完整的逐节点状态机。

## 9. 内存、引用和拷贝边界

图像数据只在 BSP 管理。pool 持有可写 shared_ptr，发布为 shared_ptr<const frame_buffer>；下游排队和正在写入都持有引用。只有所有消费者释放后，pool 才能再次使用该块。

一对多不会为每个下游复制整帧。文件 write 仍会经过操作系统写入路径，本实现不声称磁盘 DMA 零拷贝。frame_buffer 的 const 引用是约定的一部分，BSP 生产者不得绕过池检查改写仍在用的字节。

15 个缓冲与 15 个队列项是不同上限：正常链路还可能有一帧正在写，因此源可能先耗尽 15 块缓冲，而不是等文件队列到达 15。测试以单独快速入队验证满队列丢新帧策略，不将正常链路必须出现队列满当作要求。

BSP 控制接口串行调用；生产线程与文件线程通过队列互斥、智能指针及缓冲访问锁协作。不支持任意线程同时 start/stop/deinit。

## 11. 异常复现与日志定位

### 11.1 文件无法打开

路径指向不存在目录，例如 `/nonexistent-hal-directory/frame.yuv`。file.start 打印 `[file_save] open <path>: <errno文本>` 并返回 -6；pipeline 不启动源，清理已经成功启动的其他节点。

### 11.2 运行中写入失败

Linux 使用 `/dev/full` 作为路径。文件打开可成功，write 失败。日志为 `[file_save] write <path>: <原因>; pipeline remains running, failed frames are discarded`。本地 faulted=true、failed 递增，源继续运行，不自动停止 pipeline。

### 11.3 缓冲池耗尽或队列满

池的 15 块全部被下游持有时，源跳过当前周期，dropped 递增，无阻塞等待。文件队列达到上限时拒绝新帧，文件 dropped 递增。二者统计含义不同，不得混为一个丢帧原因。当前默认 Demo 不输出这些统计，测试通过具体适配器/BSP 接口观测。

本轮编译中曾发现新日志代码换行字符生成错误，已修正并重新编译测试；这不属于原工程运行故障。未处理或声称修复 SEE0115 的任何异常。

## 12. 容易疏漏的点与遗留风险

1. HAL 端口不是软件帧通道，不要为了扩展节点把 data_callback 或 BSP buffer 放回 HAL。
2. 必须先启动下游、再启动源；停止反向进行。文件节点 stop 之前，源必须已 join，防止停止排空期间又来帧。
3. 智能指针引用只决定生命周期，不自动授权改写。只读共享、池空闲判断和访问锁要共同遵守。
4. 队列必须保存拥有使用权的引用，不能替换成暂存裸指针；满时丢新帧而非丢旧帧。
5. init 先于 connect，因此当前初始化顺序不是最终图的上下游顺序。不要将 start/stop 的拓扑保证误套到 init。
6. remove_node 当前要求 pipeline 已 deinit；仅 stop 后仍不能移除。跨 pipeline 共享和 sub_pipeline 尚未实现。
7. pause/resume 均未实现；set_fps、动态尺寸、格式协商、运行中重连、ISP 黑白化也未实现。
8. 文件异常状态是本地状态，pipeline.stop 成功不等于文件保存成功。App 还未提供通用故障查询接口。
9. 部分写入后发生错误可能留下不足一帧的数据，后续继续写入无法保证裸文件帧边界可恢复。当前没有截断回退或损坏标记。
10. 写入采用阻塞文件描述符，普通本地文件验证通过，但若文件系统长期卡在 write，stop 的 join 没有超时保障；异常抛出或内存不足也没有完整工作线程恢复机制。
11. 初始化和启动失败清理未建立完整逐节点状态追踪，回滚错误未汇总；析构也不报告清理失败。不要视为覆盖所有后端失败组合。
12. 当前链接到可执行文件，不是稳定 ABI 动态库交付；没有 .so 与不同版本 App 混用验证。公共虚函数和对象布局仍在预研演进。
13. C++ 标准库路径和 BSP 的 POSIX open/write/close 面向本地 Linux，其他操作系统需另行适配。
14. 裸 I420 文件不保存尺寸、时间戳或 FPS，播放时必须外部指定；3 秒帧数不是精确 90 的契约，文件 start 会覆盖旧内容。
15. 一对多测试验证写入帧数和文件大小相等，首帧像素检查是独立测试，不是对两文件逐字节比较。
16. 图像池固定分配不代表完全没有逐帧小对象分配：分发临时 vector、deque 元素和引用计数操作仍有成本；硬件性能和缓存一致性未经验证。
